### 后续切片顺序

#### 1. 删除协议（已完成）

先补齐 `remove_component` 和 `remove_connection` 的端到端协议，包括 TypeScript 类型、C++ 请求处理、Electron IPC、协议测试和文档。

验收标准：

- 删除 Component 后，领域层保留相关 Connection，并将其识别为 dangling；
- 删除 Connection 不删除两端 Component；
- 结构修改后重建 `Simulation` 快照；
- 悬空连接不参与仿真，但可以查询、删除或重新连接；
- 不存在的身份和缺失字段返回稳定、可展示的错误。

#### 2. 画布删除与撤销（已完成）

将协议删除能力接入编辑器模型，实现 Delete/Backspace 删除选中对象、清空确认以及 Ctrl/Cmd+Z 撤销。编辑器可以把“删除元件并更新相关视觉连线状态”作为一个可恢复的复合命令；底层领域操作仍必须保持 Connection 独立生命周期的规则。

设计采用 `EditorSession` 深模块（见 [ADR 0007](decisions/0007-editor-session-and-stable-editor-ids.md)）：Vue 只使用稳定的 editor ID 和 `deleteSelection()` / `undo()`，不接触临时 engine ID 或原始协议响应。删除 Component 时引擎保留相关 dangling Connection，编辑器在最后端口位置继续显示对应悬空 Wire；撤销先使用新的 engine ID 重建 Component 和 Connection，全部成功后再清理旧 dangling Connection。删除和撤销命令串行执行，协议失败通过补偿处理；补偿失败时进入恢复状态，不静默覆盖编辑器快照。

该设计依赖 ADR 0003 的 dangling Connection 不占用 live 输入端口语义。当前固定 AND 示例已实现单选择删除、带确认的清空事务、撤销和重做；确认前不调用引擎，清空作为单个历史帧提交，部分失败执行补偿，补偿失败进入恢复状态。多选和项目加载沿用同一 Interface 继续扩展。

验收标准：

- 删除 Component 后画布立即更新，相关视觉连线保留并明确显示悬空端点；
- 撤销恢复 Component、位置、属性和相关连接；
- 清空画布需要确认，Esc 可以取消清空确认或当前选择；连接草稿的 Esc 取消随下一切片交付；
- 领域层的 dangling Connection 规则不被 UI 逻辑绕过。

## 后续阶段

### Phase 4：时序逻辑

实现 Clock、D Flip-Flop、离散 tick、上升沿、reset 和状态快照。时序行为完成前，`clock` 和 `d_flip_flop` 只作为结构元件，不应在 UI 中伪装成可运行的时序仿真。

本阶段 D Flip-Flop 的端口位宽固定为 1，Phase 4.5 也不改变这一点。多位寄存器需要由拆线器把多位拆开、接逐位 D Flip-Flop、再用合线器合并来表达，画布会更啰嗦，但不需要在总线落地后重做一次时序元件。

核心规则：

- **上升沿由端口跳变判定**：DFlipFlop 在 `clock` 端口的值相对上一 tick 发生变化时采样 `d` 并更新 `q`。Clock 元件只是产生周期性 `0 / 1` 的信号源，在引擎里和普通 Input 没有本质区别；
- 这条规则让时钟可以经 Port 传入。Phase 5.5 的 Subcircuit 不允许内部出现 Clock，展平后外部时钟接到子电路内部的 Input 元件上，端口跳变判定仍然成立；
- 结构变更重建 `Simulation` 快照的行为需要更细的 reset 语义（[ADR 0004](decisions/0004-json-lines-engine-session.md) 遗留的待明确项），至少要区分「清空全部运行时状态」与「保留时序状态」两种情形。

交付切片，全部完成后才视为本阶段完成：

1. 引擎：`Simulation` 引入 tick 与逐元件的前值快照，DFlipFlop 按端口跳变采样，Clock 作为周期性信号源；
2. reset 语义：明确结构变更、显式重置、引擎重启三种情形下 `SimulationState` 的保留范围，补齐 C++ 单元测试；
3. 协议与文档：tick 推进、连续运行控制和 reset 的请求与响应，同步更新 TypeScript 类型、`docs/protocol.md` 和协议测试；
4. 前端：连续运行 / 暂停 / 继续的真实状态转换、运行中的步数与时钟信息，并解除元件库中 Clock 与 D Flip-Flop 的禁用；
5. 端到端：一个带 Clock 的 D Flip-Flop 电路跑通连续运行，补齐回归测试和截图基准。

验收标准：

- Clock 驱动一个 D Flip-Flop 时，`q` 只在 `clock` 的上升沿变化，其余时间保持不变；
- 时钟来源不限于 Clock 元件：用 Input 元件切换 `0 / 1` 驱动 `clock` 端口时同样产生边沿；
- “开始连续运行 → 暂停仿真 → 继续仿真”三态转换有真实引擎状态支撑，暂停期间不推进 tick，继续后从暂停处的状态接着跑；
- 结构变更后 `SimulationState` 的保留范围有明确且可测试的语义，不出现“删掉一个无关元件导致全部时序状态丢失”；
- 没有 Clock 连接的 DFlipFlop 不更新，并给出结构提示；
- 类型检查和非视觉自动化测试通过 `pnpm verify`。

四项原先「待确认」的问题已在 Phase 4 的规格（issue #18）里定下，不再作为实现前的阻塞项：

- **tick 由协议上的显式 `tick` 请求驱动。** 引擎侧不引入定时器或后台线程，连续运行由前端反复发 `tick` 表达，每一步都能用「一行 JSON 进、一行 JSON 出」复现；
- **Clock 的周期固定为两个 tick**（每 tick 翻转一次，初值 `0`），本阶段不提供频率、分频或相位配置；
- **`reset` 是独立请求**，与「结构变更保留运行时状态」是两种可区分、可测试的行为；
- **`tick` 的响应带回全部输出端口的信号快照**，用途是让运行循环每步只有一次跨进程往返；本阶段不做时序状态的保存与恢复，引擎重启后不回放触发器状态。

2026-09-18，切片 2 的结构变更状态保留（issue #23）结掉了 [ADR 0004](decisions/0004-json-lines-engine-session.md) 留给时序逻辑阶段的遗留项：

- [x] 引擎：`Simulation` 不再按值持有 `Circuit` 副本，改为持有引用；结构变更走新的 `reconcile`，按元件身份重新推导仿真状态——仍然存在的 `PortId` 保留当前值，消失的端口连同它的值一起丢弃，新出现的端口按初始值建立（Clock 的 `out` 为 `0`，其余输出为 `X`），仍然存在的 `DFlipFlop` 保留它的 `q` 与 `clock` 端口上的前值。已推进的步数不归零：结构变更不是重置；
- [x] 引擎：删除元件时同时裁剪两处残留——状态表里已删除元件的输出端口，以及时钟前值表里已删除 `DFlipFlop` 的条目。这两处此前因为「每次都重建整个 `Simulation`」而不可达，保留状态后必须主动裁剪；
- [x] 工作区：`rebindSimulation` 不再清空读数，改为按身份保留并裁剪；只有拓扑真的变了才算结构修改（移动元件、改 Route 与改线色不分配新的引擎身份），结构修改把连续运行切到 `paused`，由用户按「继续」接着跑；
- [x] 测试：C++ 侧新增能区分「保留」与「重建」的断言——删除一个无关元件后，保留下来的 Input 的已提交值、以及跑出来的 `q` 都必须还在（旧实现在这里会清成 `X`）；工作区侧同样覆盖「读数跨结构变更保留」与「拓扑与几何的区分」；
- [x] 文档：新增 [ADR 0019](decisions/0019-tick-driven-by-protocol-and-state-kept-by-identity.md) 记录本阶段的三个选择（tick 由协议显式驱动、只有 `0 → 1` 采样、结构变更按身份保留状态），它同时修订 ADR 0004 的第一版规则；`docs/protocol.md` 与 `docs/architecture.md` 的生命周期约定同步更新。

已知限制：撤销删除会用新的引擎身份重建被删元件（[ADR 0007](decisions/0007-editor-session-and-stable-editor-ids.md)），因此按身份保留救不回撤销恢复的 `DFlipFlop`——它的 `q` 回到 `X`。规格明确接受这一点。

同一批里还有切片 2 的显式重置（issue #22）：引擎 `reset` 把 `SimulationState` 整份清回初始值，`Circuit` 结构不动；工作区新增 `reset()`，运行中同样可用（同步取消已排定的下一拍）；键盘等价路径是 `F8`。它与「结构变更按身份保留」互为反例，因此两条路径各有独立断言。

第一版明确不做：多位 D Flip-Flop（由 Phase 4.5 的拆线器组合表达）、Clock 分频或可编程时钟、建立/保持时间等模拟时序参数。

### 已交付（切片 5）

2026-09-18，切片 5 的端到端回归与截图基准（issue #24）给本阶段留下可重复的基线：

- **波形面板在本阶段不逐 tick 记录。** 连续运行时画布会逐拍更新，但波形历史只记录用户发起的推进——单步与输入切换各追加一点，自动 tick 不追加，所以运行中波形列不会增长。由仿真状态产生的逐 tick 波形属于 Phase 5 切片 4；
- **撤销会丢掉触发器状态。** 撤销删除会用新的引擎身份重建被删元件（[ADR 0007](decisions/0007-editor-session-and-stable-editor-ids.md) 的补偿事务），新身份的 `q` 从 `X` 开始，需要在时钟上再走一个上升沿才会重新采样。本阶段不改变这条设计。

切片 5 的本阶段部分到此完成。引擎重启后的时序状态重建仍依赖 Phase 5 的文档推送路径。

### Phase 4.5：多位 Port 与总线

阶段目标是让单个 Port 和 Connection 承载多位信号，减少 ALU 这类 Subcircuit 的端口数量，并让位宽在画布上可读。设计取舍见 [ADR 0015](decisions/0015-width-as-port-attribute.md)、[ADR 0016](decisions/0016-strict-port-width.md) 和 [ADR 0017](decisions/0017-paired-splitter-and-merger.md)。

本阶段排在 Phase 4 与 Phase 5 之间是有意的：波形记录和项目文件正是改动成本最高的两处，而它们恰好是 Phase 5 的全部内容。总线先落地，Phase 5 一次按多位值设计，项目文件也就不会出现「v1 只有标量、v2 才有多位」的兼容包袱。

相对 Phase 4 的代价则必须承认：Phase 4 会先落地 tick 与逐元件的前值快照，而 `SignalValue` 在本阶段从三值标量变成逐位多位值，`SimulationState`、边沿检测和 tick 传播都要跟着改一次。这个改造量算进本阶段的工作量，不因此把引擎部分提前到 Phase 4。

核心规则：

- 位宽是 Port 的固有属性，不引入 Bus 领域对象；位宽为 1 的 Port 与现在完全等价；
- 值是逐位三值的：一个 N 位值是 N 个独立的 `0 / 1 / X`，某一位未知不影响其余位；
- 位宽严格声明，两端位宽不同直接拒绝连接，不做隐式扩展或截断；
- 协议中的信号值统一为字符串（`"0"`、`"1"`、`"X"`、`"1010"`、`"X1X0"`），长度必须等于端口位宽；
- 端口清单是位宽的唯一权威来源，消除现在「引擎 `portsFor` 与前端 `ComponentDefinitionRegistry` 各写一份且互不校验」的分歧：`add_component` 可选携带端口清单，省略时引擎回退到内置定义；`component_added` 回传该 Component 实际的端口清单，前端不再内置一份端口定义，`ComponentDefinitionRegistry` 只保留展示元数据；
- 位宽在创建后仍可修改：新增 `set_port_width` 请求（或等价的 `update_component`），保留 Component 与 Connection 的引擎身份；位宽变化后不再匹配的 Connection 自动转为 DanglingConnection，沿用 ADR 0003；
- 逻辑门保持 1 位，不随输入宽度自动变宽。多位运算由拆线器和合线器落到逐位元件上；
- 拆线器和合线器是两个单向元件。引擎没有双向端口，Logisim 那种拆合一体的元件在这里做不出来；
- 拆线器把一条多位输入拆成若干条位区间输出，合线器反向合并。位区间必须完整覆盖输入总线的每一位且互不重叠；
- 位编号为 `[N-1:0]`，位 0 是最低位；画布上 MSB 在上、LSB 在下；总线文本用二进制，使逐位 `X` 保持可见；
- 位宽不改变线路外观。线路颜色由用户通过预设选择（延续 ADR 0013）；线宽与线型目前固定，不随信号值变化，放开它们需要单独的决策。位宽由端口标签的位区间和信号文本表达。

交付切片，全部完成后才视为本阶段完成：

1. 引擎：`Port` 增加位宽、`SignalValue` 变为逐位多位值、`addConnection` 增加位宽校验、`addComponent` 支持携带端口清单、新增 `set_port_width`，补齐 C++ 单元测试；
2. 协议与类型：信号值统一为字符串，`component_added` 回传端口清单，`isSignal`、`docs/protocol.md` 和前端类型同步更新，前端不再内置端口定义，补齐协议测试。文件序列化格式由 Phase 5 决定，不在本阶段；
3. 拆线器与合线器：引擎求值、位区间端口、元件库「总线」分类、画布形状沿用 Subcircuit 的形状规则（端口间距 32、最小宽度 148、高度按端口数增长）。协议 `kind` 沿用现有命名风格取 `splitter` 与 `merger`。新放置的拆线器默认 8 位输入拆成八个 1 位分支；合线器与它对称，默认八个 1 位输入合成一条 8 位输出；
4. 画布与检查器：端口标签显示位区间，位宽成为检查器的第一个可编辑属性（Input / Output 元件，以及拆线器的位区间列表），提交走 `set_port_width`。同步更新 `docs/design/frontend-design-system.md`——它现在把「总线」列在第一版视觉范围之外，需要改为收录多位 Port 的标注规则；
5. 输入设置：Input 元件按位展开为方形按钮，每行八列，左键切换 `0 / 1`、右键设为 `X`，可展开收起；1 位 Input 同样渲染为单个方形按钮，元件标签在位按钮组上方；
6. 波形：`WaveformPoint` 改为按编辑器 ID 索引的动态信号集合，行由场景投影生成，多位信号按二进制显示；
7. 端到端：一条多位数据通路跑通仿真，补齐回归测试和截图基准。

验收标准：

- 位宽为 1 的既有电路在本阶段完成后，行为、协议和外观均不变；
- 一条 N 位 Connection 传输一个逐位三值，`X` 只影响未知的那几位，其余位正常传播；
- 位宽不同的两个 Port 无法连接，并给出可展示的原因；
- 改位宽后，不再匹配的 Connection 转为 DanglingConnection 并可重接，其余 Component 与 Connection 保持原引擎身份；
- 新放置的拆线器与合线器按默认位宽与分支数直接可用，无需先改配置；
- 拆线器与合线器的位区间组合完整覆盖且互不重叠，越界、重叠或漏位都给出可展示的原因，不产生半成品快照；
- 输入设置可以为任意 Input 元件的任意一位设置 `0`、`1` 或 `X`，鼠标与键盘均可完成；
- 波形记录全部 Input 元件和输出信号，不再局限于前两个输入，多位信号逐位可读；
- 多位电路的帧耗时仍满足 Phase 3 的基准；
- 类型检查和非视觉自动化测试通过 `pnpm verify`。

第一版明确不做：常量字面量、加法器、MUX 和比较器等运算元件；多位 D Flip-Flop；多位值的十六进制或十进制显示；传统波形形态的总线菱形带渲染；位宽上限；任何隐式位宽转换。

### Phase 5：波形和持久化

实现由仿真状态产生的简单波形、项目文件、版本字段和加载校验。当前前端中的波形历史是示例交互反馈，不能替代这一阶段的持久化和真实时序波形。

项目文件格式设计时必须满足 Phase 5.5 的前提：文件带版本字段，Component 记录能承载按类型扩展的数据（例如 Subcircuit 的引用路径、缓存端口清单和显式端口顺序）。具体字段由本阶段决定。Phase 4.5 先于本阶段完成，因此波形和项目文件从一开始就按多位值设计，不需要为标量快照保留兼容路径。

核心规则：

- **路径规范化规则必须在本阶段定死**：大小写敏感性、路径分隔符、是否跟随符号链接、相对路径的基准目录。Phase 5.6 的文档身份是「规范化后的绝对路径」，规则不唯一则「同一份 Project 是否已打开」无法回答；
- **编辑器文档要能整体推送到引擎**：加载项目、重建被重启的引擎进程、以及 Phase 5.6 的引擎按文档重建，共用同一条推送路径。这条路径在 Phase 5.6 不重复实现；
- 视口不进入项目文件（[ADR 0008](decisions/0008-layered-canvas-scene-rendering.md)、[ADR 0009](decisions/0009-manual-orthogonal-wire-routes.md)）；
- 首启行为在本阶段改变：启动进入空状态加最近项目，AND 示例降为「加载示例」入口，[ADR 0005](decisions/0005-frontend-design-language.md) 的「首次启动自动加载并运行 AND 示例」到此结束。

交付切片，全部完成后才视为本阶段完成：

1. 项目文件格式与版本字段、加载校验和错误展示；
2. 保存 / 另存为 / 打开 / 新建，以及最近项目入口；
3. 编辑器文档推送到引擎的完整路径，并给出加载、重载与引擎重启的端到端时延预算（Phase 5.5 起这条路径还要处理展平后的电路）；
4. 由仿真状态产生的波形，按 tick 记录，取代当前的示例波形历史；
5. 首启行为改为空状态加最近项目，AND 示例改为「加载示例」入口；
6. 端到端：一份多位电路保存后重新打开，电路结构、仿真结果与波形与保存前一致。

验收标准：

- 保存并加载项目文件（含元件位置、Waypoint、位宽与端口清单）后，电路结构、仿真结果和波形与保存前一致；
- 版本字段缺失或过高时给出可展示的原因，不产生半成品快照；
- 路径规范化规则有单元测试覆盖，同一文件的不同写法被识别为同一份 Project；
- 把一份 Project 推送到引擎的时延有明确预算，并在基准中覆盖；
- 保存或加载失败时保留可恢复路径，不丢失当前编辑器状态；
- 类型检查和非视觉自动化测试通过 `pnpm verify`。

待确认（实现前必须定）：

- Editor ID 是否写入项目文件；
- 元件位置与 Waypoint 的存储形态；
- 最近项目的存储位置与保留条数。

第一版明确不做：自动保存、崩溃恢复、跨文件格式版本的向前兼容（只保证同一版本内互相打开）。

（「保存和加载项目文件」原先列在 Phase 3 的未完成清单中，依赖本阶段的项目文件能力，因此移到本阶段。）

### Phase 5.5：层次化电路

阶段目标是把一个已保存的 Project 作为 Subcircuit 放入另一份 Circuit 中复用，术语见 `CONTEXT.md`，设计取舍见 [ADR 0014](decisions/0014-subcircuit-by-reference-flattened-simulation.md)。依赖 Phase 4（子 Project 内允许 DFlipFlop）、Phase 4.5（多位 Port）和 Phase 5（项目文件）。Phase 4.5 之后端口清单包含位宽，展平时按位宽对齐。

核心规则：

- Subcircuit 按相对路径引用，父 Project 缓存端口清单；文件缺失或校验失败显示为"未解析"并不参与仿真；
- 子 Project 的 Input / Output 元件构成对外 Port，名字取自标签，位宽取自该元件，默认按纵坐标排序，可显式覆盖；不允许 Clock；
- 画布形状为左进右出的矩形，端口间距 32，最小宽度 148，宽度按最长端口名自适应并向上取整到网格；标签显示 Project 文件名；
- 仿真在加载时展平为普通元件，引擎和协议不新增请求类型；
- 允许多层嵌套，引用成环时拒绝加载该 Component；
- 子 Project 变化通过手动"重新加载子电路"命令生效，作为可撤销历史帧；端口按名字匹配，对不上的 Connection 变为悬空。

交付切片，全部完成后才视为本阶段完成：

1. 纯 TypeScript 展平函数与单元测试：输入父文档与子文档，输出扁平元件、Connection 列表和外部 Port 映射，含引用环检测和接口校验（空标签、重名、含 Clock）；
2. `ComponentDefinition` 支持数据驱动的端口列表与尺寸计算，画布按上述形状规则渲染 Subcircuit，Editor ID 到 Engine ID 的映射支持一对多；
3. 元件库新增"子电路"分类，通过文件选择器添加 Subcircuit，支持删除、撤销和重做；
4. 保存加载时的引用解析、端口清单缓存、"未解析"状态、按名字匹配 Connection 和手动重载命令；
5. 端到端：多层嵌套的 ALU 示例 Project 跑通仿真，检查器显示引用路径、解析状态和端口清单，补齐回归测试。

验收标准：

- 同一子 Project 在父 Circuit 中放入多份时，各自独立仿真，DFlipFlop 状态互不影响；
- 修改子 Project 并在父 Project 中重新加载后，名字未变的 Port 上的 Connection 保留，其余变为 DanglingConnection 并可重接；
- 子 Project 文件缺失时父 Project 仍能打开，Subcircuit 以缓存端口显示并标记为未解析；
- 引用成环、空标签、重名标签、内部含 Clock 均给出可展示的原因，不产生半成品快照；
- 展平后达到 500 个 Component / 1,000 条 Wire 时，仍满足 Phase 3 的帧耗时基准；
- 展平并推送到引擎的时延满足 Phase 5 定下的加载预算；
- 类型检查和非视觉自动化测试通过 `pnpm verify`。

第一版明确不做：下钻编辑子 Project、查看某个 Subcircuit 内部实时信号、四边端口布置、自动扫描库目录。

### Phase 5.6：多文档与下钻

阶段目标是让多份 Project 同时处于打开状态，并沿着 Subcircuit 的引用关系在它们之间导航；在此基础上以只读方式查看某个 Subcircuit 实例内部的实时信号。方案细节见[多文档与下钻设计](design/multi-document-and-drill-down.md)，同步语义见 [ADR 0018](decisions/0018-subproject-changes-do-not-propagate-automatically.md)。

依赖 Phase 5（项目文件，提供"打开"这个动作和 Project 身份）与 Phase 5.5（Subcircuit 按引用组合）。本阶段不引入新的领域对象，**也不新增任何引擎请求类型**。

核心规则：

- 工作区以标签页承载多份打开的 Project，始终只有一份活动文档；不做分屏，不做多窗口；
- 同一份 Project 只存在一个标签。已保存文档的身份是它的规范化绝对路径；未保存的文档同样占有一个标签，以临时身份标识（如「未命名 1」），但它不能被 Subcircuit 引用，也不参与按路径去重。保存时身份从临时切换为路径，该路径已在标签栏时合并到已有标签；
- 每份文档持有独立的引擎进程、独立的 `EditorSession` 和独立的视图状态；切走的文档冻结但保留信号快照、波形历史和 DFlipFlop 状态；
- 双击画布上的 Subcircuit 打开它引用的子 Project，作为一份完全同权的可编辑文档；检查器提供键盘可达的等价入口；
- 子文档记录一跳来源，任何方式切回父文档都选中并居中该来源实例；不引入导航栈；
- 子 Project 的未保存改动只存在于子文档自己的标签页，不改变父电路使用的展平副本；保存后父文档出现"需重新加载"提示，重载仍由用户显式触发；
- "未解析"的 Subcircuit 禁止下钻，并给出可展示的原因；
- 实例内部实时信号以只读信号表呈现在检查器中，显示的是**父电路展平副本**的状态，不是子文档标签页的状态。

交付切片，全部完成后才视为本阶段完成：

1. 引擎多文档承载：Electron 主进程的 `EngineClient` 从模块级单例改为按文档管理的进程池，补齐懒启动、按文档的健康检查、关闭回收和崩溃隔离。进程重启后的引擎状态重建复用 Phase 5 的「编辑器文档推送到引擎」路径，本阶段不重复实现；
2. 工作区与标签页：文档身份与单选去重、每文档一份 `EditorSession` 与视图状态、信号与波形的键空间加文档维度；
3. 下钻与来源：画布双击与检查器入口、来源记录与返回高亮、未解析禁用下钻、未保存改动不穿透、保存后的"需重新加载"提示；
4. 实例内部实时信号：检查器中的只读信号表。

验收标准：

- 同时打开两份 Project 时，各自的元件、连线、撤销栈、视口和选中互不干扰；同一份 Project 再次打开只激活已有标签；
- 新建的未保存文档拥有一个标签，以临时身份标识；保存后身份切换为规范化路径，该路径已在标签栏时合并到已有标签而不产生第二个标签；
- 强制结束某份文档的引擎进程，其余文档的仿真不受影响，该文档进入"引擎不可用"状态并可重启；重启后的重建复用 Phase 5 的推送路径，并满足同一份加载时延预算；
- 切走的文档恢复后，信号快照、波形历史与 DFlipFlop 状态与离开时一致；两份文档中同名的 editor ID 不会互相覆盖；
- 从子标签返回父文档时来源实例被选中并居中；关闭父标签后子标签的来源记录被清除，退回"从文件打开"；
- 子 Project 的未保存改动不改变父电路的展平副本；保存后在父文档中出现"需重新加载"提示，执行已有的"重新加载子电路"后，名字未变的 Port 上的 Connection 保留，其余成为 DanglingConnection 并可重接；
- 未解析的 Subcircuit 下钻入口禁用，并给出可展示的原因；
- 选中已解析的 Subcircuit 时，检查器显示其展平副本的实时信号；同一子 Project 在父电路中被放入多份时，两份状态互不影响；
- 活动文档的帧耗时仍满足 Phase 3 的基准，且与打开的文档数无关；
- 类型检查和非视觉自动化测试通过 `pnpm verify`。

第一版明确不做：分屏并列显示两份电路；同一份 Project 开多个标签；下钻的导航栈或多级面包屑；把侧栏"层级"页改成层次树；在父画布上就地展开实例内部；以独立只读文档查看实例内部；跨文档复制粘贴或拖拽元件；多窗口；被引用子 Project 的自动重载。

### Phase 6：工程化和发布

完善 CI、日志、错误处理、打包、发布文档和回归测试。
