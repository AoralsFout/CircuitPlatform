# ADR 0020：端口清单是位宽的唯一权威来源

## 状态

已确认

## 背景

[ADR 0015](0015-width-as-port-attribute.md) 把位宽定为 Port 的固有属性，[ADR 0016](0016-strict-port-width.md) 定下位宽严格声明、不做隐式转换，[ADR 0017](0017-paired-splitter-and-merger.md) 定下拆线器与合线器。这三条决策在落地时留下了四处本文档记录的具体形状——它们不是重新决策，而是把上面三条落到实现时必须选定的做法。

落地之前，端口定义有两份且互不校验：引擎的 `portsFor` 与前端 `ComponentDefinitionRegistry`。这个分歧真实地伤过一次——前端给 D Flip-Flop 声明 `clk`，引擎期望 `clock`，只因为该元件当时被标为不可用才没暴露。位宽进来以后，如果还保留两份副本，分歧面会翻倍。

## 决策

### 一、端口清单是位宽的唯一权威来源

`add_component` 可以携带一份可选端口清单，省略时引擎回退到内置定义；`component_added` 必带回该 Component **实际的**端口清单。前端不再独立声明一份无人校验的副本，`ComponentDefinitionRegistry` 只保留展示元数据。

端口的**存在与位宽**由引擎的清单决定；**画在哪、显示成什么**是展示元数据的事。两者分开之后，前端的端口几何不再需要跟着端口名走：展示定义里没有登记的端口会落到通用排布规则上，只会换个位置画，不会凭空多出或少掉一个端口。运行时要读哪些端口同样从清单推导，因此也不再有第二份 `kind → 端口名` 的表。

### 二、`set_port_width` 的载荷是整份端口清单

改位宽的请求名沿用路线图的 `set_port_width`，但载荷与 `add_component` 的可选端口清单**同构**，语义是「整体替换该 Component 的端口清单」，而不是「改某一个端口的位宽」。

理由是这两件事在用户眼里是同一件事：Input / Output 的「改位宽」与拆线器的「改位区间列表」都是编辑一份清单。而拆线器的某一分支区间改了以后其余分支必须跟着重算，按单端口下发的形状根本表达不出一次合法的整体变更。

响应回传替换后的清单，以及**因本次改宽而转为悬空**的 Connection 身份——即改宽前不悬空、改宽后悬空的那些。改宽前就因为端点缺失而悬空的连接不是这次变更的结果，调用方本来就知道它们。

### 三、位宽不匹配的 Connection 归入悬空

悬空的判定从「端点无法解析」扩展为「端点无法解析，**或**两端 Port 的位宽不再相同」。这是对 [ADR 0003](0003-connections-have-independent-lifecycle.md) 的扩展而不是推翻：「悬空」在领域里一直是「不参与仿真、但可查看、可删除、可重接」这一种表达，位宽不匹配正落在这个集合里，不必另造「失效连接」概念。

引擎求值时同样跳过位宽不匹配的 Connection。改宽后不再匹配的输入端口不再占用该输入端，因此可以像删除元件后的悬空连接一样被重接。

### 四、位宽变化的端口按初值重建

`reconcile` 按 `PortId` 保留值的规则在多位下多一个前提：值的长度必须等于端口当前的位宽。位宽变了的端口无法保留旧值，按初值重建——Clock 的 `out` 是等宽的全 `0`，其余是等宽的 `X`。

不采用「按位对齐保留低位」：它需要发明一套对齐规则（从哪一端对齐、旧值比新位宽长时丢弃哪几位），而没有任何用例要求它。

## 未采用的方案

### 前端保留一份端口定义并把位宽同步过去

不采用。它把「两份互不校验的副本」换成「两份约定互相同步的副本」，分歧仍然只靠约定维系。位宽进来后分歧面翻倍，正是本阶段要避免的事。

### `set_port_width` 按单端口下发

不采用。见决策二：拆线器改一个分支会让其余分支必须重算，按单端口的形状表达不出一次合法的整体变更，调用方只能拆成多次请求，中途的清单不自洽。

### 为位宽不匹配另造「失效连接」概念

不采用。领域里已经有一个「不参与仿真、可查看、可删除、可重接」的表达，多一个近义词只会让调用方多一次分支判断。

### 改宽后按位对齐保留低位

不采用。见决策四。

## 后果

- `docs/protocol.md` 的请求与响应表随本次落地同步，`add_component` 与 `component_added` 的形状变化是破坏性改动。此刻动手是安全的——Phase 5 尚未开始，磁盘上没有任何需要兼容的项目文件；
- 前端对内置元件类型**不再自己生成端口清单**。带清单的请求只用在数据驱动的元件上（拆线器与合线器），内置类型一律省略清单、由引擎回退；
- 改宽后按初值重建的端口，其旧值不会以任何形式保留，用户因此需要重新设置输入。这是决策四的直接代价，也是 Phase 5 的文档推送路径要接上的地方；
- 检查器需要能编辑位宽，这是 [ADR 0014](0014-subcircuit-by-reference-flattened-simulation.md) 所说的「第一版不引入没有实际用例的可编辑属性」的第一个真实例外；
- 端口几何成为展示元数据里的布局条目加一条通用排布规则，数据驱动的元件不需要在展示定义里登记端口。

## 后续变更

2026-09-18 落地本决策的切片（GitHub issue #28）新增了两条本文档未预先写下的实现规则，一并记在这里：

- **端口几何由通用排布规则推导**。展示定义按引擎端口名索引一份布局表，表里没有的端口回退到「同方向的端口在元件垂直中线上按 24 间距均分、输入贴左、输出贴右」。这条规则复现了既有元件的全部端口坐标，因此表里只需要登记规则复现不了的形状（D Flip-Flop 的 `q` 与 `d` 对齐而不是垂直居中）；
- **解析端口清单的那一层按成员名扫描，而不是按子串查找字段**。`ports` 是协议里第一个嵌套结构，按子串查找会在端口名与某个键名相同时命中字符串里的同名文本。

2026-09-18 落地「输入设置按位展开」（GitHub issue #30）时补上第三条：

- **端口清单算电路结构的一部分，而不只是身份的一部分**。工作区判断「一次绑定更新有没有真的改动结构」时原本只比元件、连接与元件类型三份**引擎身份**映射；改宽按决策一保留身份，因此那次判断会认为什么都没变，把运行时绑定留在旧位宽上——提交出去的值长度对不上，引擎以 `invalid_width` 拒绝。四份映射（含端口清单）全等才算结构没变，位宽变更因此与其它结构提交一样会暂停连续运行并重新推导绑定。这一条是决策一「端口清单一并随绑定发布」的直接推论，不是新决策。
