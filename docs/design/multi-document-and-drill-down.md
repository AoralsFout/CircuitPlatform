# CircuitPlatform 多文档与下钻设计

## 文档状态

- 版本：0.1
- 状态：已确认方向，待随实现迭代
- 适用范围：`apps/desktop`（Vue 渲染进程 + Electron 主进程）
- 依赖：[ADR 0014](../decisions/0014-subcircuit-by-reference-flattened-simulation.md)、[ADR 0018](../decisions/0018-subproject-changes-do-not-propagate-automatically.md)、[ADR 0007](../decisions/0007-editor-session-and-stable-editor-ids.md)
- 对应阶段：[Phase 5.6](../roadmap.md)

## 1. 目标与边界

本设计让多份 Project 同时处于打开状态，并沿着 Subcircuit 的引用关系在它们之间导航，然后在此基础上只读查看某个 Subcircuit 实例内部的实时信号。

它解决的是**导航**问题，不是**编辑**问题：本设计不引入任何新的电路编辑能力，也不扩展引擎的求值能力。

三件事同属一个阶段，但按依赖分层交付，且可以停在任意一层：

1. **层次导航**——沿着 Subcircuit 引用关系在父子电路之间来回。这是真实场景：用户在 CPU 里双击 ALU、改完返回。
2. **并列多文档**——同时打开两份不相关的 Project。这是第一层的廉价副产品，共用同一套标签页机制。
3. **只读实例信号**——查看某个 Subcircuit 实例内部的实时值。这是唯一可能触及仿真架构的一层，也是可以整体砍掉的一层。

### 与相邻阶段的边界

本阶段**不新增任何引擎请求类型**。这条延续 ADR 0014 的做法：展平让层次化不需要引擎感知，多文档让每份文档各持一个引擎进程即可，两者都不需要协议演进。

本阶段的全部前提是 Phase 5（项目文件）提供的"打开"动作和 Project 身份，以及 Phase 5.5（层次化电路）提供的 Subcircuit 引用与展平。

## 2. 术语与对象

本设计**不引入新的领域对象**。[CONTEXT.md](../../CONTEXT.md) 里的 **Project** 就是"文档"：它是用户保存和打开的工作单元，一个 Project 恰好包含一份 Circuit。"打开"这个动词本来就属于 Project。

本设计引入的是一个 **UI 概念**，暂称**工作区**：它承载"当前打开了哪些 Project、哪一个是活动的"。工作区是应用级状态，不是领域对象，因此不进 `CONTEXT.md`。

其余在本设计中反复出现的词都是 UI 词，同样不进术语表：

- **文档**：工作区中一份已打开的 Project。文档与 Project 一一对应，不是新对象。
- **活动文档**：当前占据画布的那一份。本设计始终只有一份活动文档。
- **来源**：一份文档是被"下钻"打开的时记录的那一跳信息——父文档 + 来源实例的 Editor ID。
- **文档身份**：已保存文档是它的规范化绝对路径；未保存文档是开标签时分配的临时身份（如"未命名 1"），保存后切换为路径。

### 文档身份为什么是路径

文档身份要回答两个问题："同一份 Project 是否已经打开"，以及"父电路引用的子 Project 是否就是某个已打开的文档"。规范化绝对路径同时答得了这两个，而且它就是 ADR 0014 里引用关系的依据——父 Project 记录子 Project 的相对路径。

**未保存的 Project 不能被引用**：它没有路径，因此不能被其他 Circuit 引用，也不能参与"是否已打开"的按路径判定。这不是本设计新增的规则，而是 ADR 0014"按相对路径引用"的直接推论——"先保存才能被复用"是这个系统里本来就成立的事。

但"不能被引用"不等于"不能成为标签"。Phase 5 的"新建"必然先产生一份未保存文档，如果它不能出现在标签栏里，最常见的起步路径就没有位置可放。因此：**未保存文档以临时身份（如"未命名 1"）占一个标签**，不参与按路径去重，也不出现在任何 Subcircuit 引用中。保存时身份从临时切换为规范化路径；该路径已在标签栏中时合并到已有标签，而不是产生第二个标签。

## 3. 呈现与导航

### 标签页，单活动文档

顶部项目栏改为标签栏。始终只有一份活动文档占据画布、侧栏和底栏。

**不做分屏。** 分屏要求侧栏、检查器、波形、输入设置全部变成"每文档一份"，而现在它们是工作区级的——把五个面板乘上文档数，成本和收益完全不成比例。

**不做多窗口。** 本阶段是单窗口多标签；多窗口是另一个维度的工作区问题，不在范围内。

### 同一份 Project 只有一个标签

再次打开一份已经打开的 Project 时激活已有标签，不产生第二个标签。理由是"同一文件两份内存状态"无法自动合并——未保存改动让它们必然冲突，这是文件编辑器的经典陷阱。代价是"对比同一份电路的两个版本"做不到，但那是 diff 视图该解决的问题。

去重按文档身份进行：已保存文档按规范化路径，未保存文档按临时身份（第 2 节），因此"保存成一个已经在标签栏里的路径"要合并到那个标签，而不是并存两份。

这条规则有一个必须一起接受的推论：**同一个子 Project 在父电路里放了多份时，从实例 X 和实例 Y 下钻得到的是同一个标签页。** 用户编辑的是同一份 Project，所有使用处都受影响。这是 ADR 0014"按引用不按拷贝"的直接结果，需要在画布或检查器上把"这是同一份文件"说清楚，否则用户会以为自己在改实例 X 的私有副本。

### 下钻的入口

- **主入口**：双击画布上的 Subcircuit 实例。
- **等价入口**：检查器中的"打开子电路"。双击只有鼠标路径，而 Phase 3 的验收标准要求平移、缩放、添加、拖动、布线和 Route 编辑都提供键盘等价路径；下钻是同类交互，不能例外。检查器本来就显示 Subcircuit 的引用路径与解析状态（ADR 0014 的要求），"打开"放那里最自然。

侧栏的"层级"页（`RailPage = "layers"`）**本阶段不改动**：既不重命名也不改语义，仍然平铺本文档的元件。把它改成层次树需要先有可见的展平层次结构，属于第 6 节那一层的工作。

### 来源记录与返回

下钻打开的子文档记录**一跳来源**：父文档 + 来源实例的 Editor ID。切回父文档时选中并居中该实例。

- **不做导航栈，也不做多级面包屑。** 标签页本身就是完整的导航状态——父文档本来就在标签栏里、可点击——所以缺的不是"返回路径"，而是"我刚从哪个实例来"。这一点也是把"下钻打开"和"从文件菜单打开同一份 Project"区分开的**唯一**信息。A→B→C 时每份文档各记一跳来源，链条自然成立；而且 ADR 0014 禁止引用成环，导航根本绕不回来。
- **高亮绑在"来源"上，不绑在某个按钮上。** 任何方式切回父文档（点标签栏、点"返回父电路"按钮）都选中并居中来源实例。用户在这里切回父文档的意图基本只有一个：刚改完子电路，想看父电路的反应。

### 关闭

- 有未保存改动的标签在关闭时确认，沿用已有的 `ClearCanvasDialog` 确认模式，不发明新的确认机制。
- 关闭父标签时，子标签的来源记录**直接清除**，它退回成"从文件打开"的样子。不级联关闭子标签（用户可能正在子电路里工作），也不保留指向已关闭文档的悬空来源——保留它会让"返回父电路"变成"重新打开一个你刚亲手关掉的文档"。
- 关闭子 Project 的标签**不影响任何使用它的父电路**：父电路跑的是展平副本，本来就独立。之后在父电路上再下钻该实例，会重新打开一份干净的标签。

## 4. 引擎承载

### 每份文档一个引擎进程

引擎当前是"一个进程 = 一份 `Circuit` + 一份 `Simulation`"（`engine/src/main.cpp`），协议里没有任何文档维度。承载多文档的三条路里：

- **每文档一个引擎进程**（采用）——协议与引擎零改动，每进程的 ID 计数器天然独立（正好匹配"每文档一个 `EditorSession`、ID 各从 1 开始"），一个文档的引擎崩溃不波及其余文档，不需要任何新的并发语义。
- **单进程多文档**——协议要加文档维度，`request_handler` 从收 `Circuit&` 改成按 key 查表。放弃了 ADR 0014 确立的"不为层次化新增请求类型"这条思路，且单点崩溃会带走全部文档。
- **单进程单 Circuit，切标签时整体重建**——必须排除：引擎侧没有任何导出电路的请求，而 `DFlipFlop` 状态在引擎里、前端只有 `EditorDocument`，切标签重建等于每次都丢掉时序状态，直接违背"切走的文档冻结但保留"。

这里有一处必须显式记录的变化：[ADR 0004](../decisions/0004-json-lines-engine-session.md) 决定「由 Electron 主进程持有**一个**长连接客户端」，本设计把它改为按文档索引的进程池。协议本身不变（stdin/stdout 上的 JSON Lines、`requestId` 匹配、一问一答），变的只是「谁持有连接」这一层。

Electron 主进程的 `EngineClient` 从模块级单例改为**按文档键索引的进程池**。要点：

- 沿用现有懒启动：某份文档的第一条请求才 spawn 它的进程；
- 健康检查按文档执行。现在健康检查复用同一条连接以避免重启进程；改为进程池后，健康检查针对活动文档的进程，没有文档打开时用一个探针进程；
- 关闭文档时结束对应进程，并清理该进程的 `requestId` 匹配表；
- 崩溃只把该文档标记为"引擎不可用"，其余文档不受影响。该文档重启后引擎 ID 从 1 重新开始，因此必须重建 Editor ID → Engine ID 映射并重置这份文档的仿真状态；
- 主进程与渲染进程之间的 `engine:*` IPC 通道需要携带文档键；`preload` 暴露的接口相应变化；
- 暂不设进程数硬上限，文档数就是上限。设计要求是**活动文档的帧耗时与打开的文档数无关**。

## 5. 状态隔离

### 每文档一份

- **`EditorSession`**：`createEditorSession` 已经是纯闭包工厂、没有模块级单例，多实例能力已经具备。要改的是组合层——`useWorkspace.ts` 的 `attachEditor` 把它固化为一份（`App.vue` 只消费快照，不持有会话），需要改为按文档实例化。
- **视图状态**：视口、选中、侧栏页、底栏 tab 每文档一份，活在标签页的生命周期内。**不写入项目文件**——这一条不是本设计新定的，[ADR 0008](../decisions/0008-layered-canvas-scene-rendering.md) 与 [ADR 0009](../decisions/0009-manual-orthogonal-wire-routes.md) 已经确认「视口不随项目持久化」。顺带澄清一处容易误读的地方：`CONTEXT.md` 说 Project 包含"编辑器布局"，指的是**元件位置与走线**（roadmap 明确"Component 位置、选中状态和视觉 Wire 只保存在编辑器模型中"）；视口是**观看位置**，不是布局，因此这里与 `useEditorState.ts` 中"视口不进入项目持久化"的注释不矛盾。
- **信号与波形**：`WorkspaceSnapshot` 的 `inputValues` 以 editor component ID 为键，`signals` 以 `${editorComponentId}:${portId}` 为键，`waveform` 则是固定形状 `{step, a, b, output}` 的单个扁平序列。**每个 `EditorSession` 的 ID 序列各从 1 开始，两份文档都会出现 `input-a`**，直接共用一个工作区会键冲突；`waveform` 即使不冲突，也会把两份文档的采样混在一条时间轴上。因此这些键必须加上文档维度限定作用域。Phase 4.5 会把 `waveform` 改成按编辑器 ID 索引的动态信号集合（[roadmap](../roadmap.md) 切片 6），文档维度要在那一个键空间里一次设计到位。

### 保持全局

主题、最近使用元件、默认线色是用户偏好，跨文档共享，维持现状。

## 6. 下钻的同步语义

完整决策见 [ADR 0018](../decisions/0018-subproject-changes-do-not-propagate-automatically.md)。要点：

- 子 Project 的**未保存**改动只存在于子文档自己的标签页，不改变父电路使用的展平副本；
- 保存后父文档出现"子电路已变化，需重新加载"提示，重载仍由用户显式触发，作为可撤销的历史帧；
- 端口匹配沿用 ADR 0014：按名字匹配，对不上的成为 DanglingConnection；
- **未解析**的 Subcircuit 禁止下钻，给出可展示的原因。没有文件就没有可打开的文档；"用缓存端口现场造一份空文档"更糟，它会造出一份与磁盘不一致、用户却以为能保存回去的写回对象。

### 三个不能合并的状态

界面需要同时表达三个**互相独立**的状态位：

| 状态 | 主体 | 含义 |
|---|---|---|
| 未保存 | 子文档 | 子文档有改动未落盘 |
| 未重载 | 父文档 | 子文档已保存，但父电路持有的展平副本是旧的 |
| 未解析 | 父文档中的该实例 | 子 Project 文件缺失或校验失败 |

前两者不能合并成一个"脏"标记——它们的主体不同，一个是子文档、一个是父文档。

## 7. 实例内部实时信号

### 呈现方式

选中一个已解析的 Subcircuit 时，检查器列出**该实例内部元件及其端口的当前实时值**。

- **不做**在父画布上就地展开实例内部：它会碰 Phase 3 的性能预算（展平后按 500 元件 / 1,000 条线计），并要求新的视口语义。
- **不做**以独立只读文档的形式查看实例内部：那要新增一种"只读文档"，而只读文档在本设计里已经被否过一次（下钻打开的子 Project 是完全同权的可编辑文档）。

信号表不需要新的渲染路径、不需要新的视口语义、不碰性能预算，却能解决真实问题——"CPU 为什么不对"的答案几乎总是一个**具体的内部信号值**，而不是内部电路的形状。

### 显示的是哪一份状态

这是本节最容易被做错的地方。展平后，同一个子 Project 在父电路中每放入一份，就在引擎里生成一组独立的元件和独立的 `SimulationState`。因此：

- 信号表显示的是**父电路展平副本**的状态，**不是**子文档标签页自己的仿真状态。这两者在同一时刻可能完全不同——尤其当子文档有未保存改动时（第 6 节）。
- 同一个子 Project 在父电路中被放入多份时，信号表分别显示各自的展平状态，`DFlipFlop` 状态互不影响（这正是 Phase 5.5 的验收标准之一）。

这条不说清楚，"查看实例内部信号"会变成一个看起来对、实际答非所问的功能。

### 只读

信号表面板不提供任何改变父电路结构的操作。

### 待确认：信号的采集方式

协议里没有批量读取信号的请求，`get_signal` 一次只取一个 Port。因此本节「不碰性能预算」的判断还缺一个前提：采样时机（每次 settle 后全量读取，还是只在面板可见时读取）与读取范围（整棵子树，还是只读可见行）。这两点必须在实现前定下来，否则这一节可能推翻活动文档的帧耗时验收。

## 8. 对相邻阶段的接口要求

### 给 Phase 5 的两条要求

一、**路径的规范化规则**：大小写敏感性、路径分隔符、是否跟随符号链接、相对路径的基准目录。文档身份是"规范化后的绝对路径"，规范化规则不唯一，身份就不唯一，"同一份 Project 是否已打开"就无法回答。

二、**未保存文档的临时身份**：第 2 节要求未保存文档也能占据标签，因此 Phase 5 的"新建"必须提供一个不依赖路径的临时身份，并保证保存时平滑切换为规范化路径、与已有同路径标签合并。另外，Phase 5 的"编辑器文档推送到引擎"路径被本阶段的引擎重启复用，不应该在这里再实现一遍。

这两条之外，**不要把下钻或多文档塞进 Phase 5 或 Phase 5.5 的验收标准**——那会让那两个阶段的范围失控，而本设计的前两层（标签页、下钻）并不需要它们做任何额外的事。

### 对 Phase 5.5 的依赖

本设计完全建立在 Phase 5.5 已经交付的 Subcircuit 引用、展平函数和一对多的 Editor ID → Engine ID 映射之上，不要求 Phase 5.5 做任何改动。

## 9. 明确不做

- 分屏并列显示两份电路；
- 同一份 Project 开多个标签；
- 下钻的导航栈或多级面包屑；
- 把侧栏"层级"页改成层次树；
- 在父画布上就地展开实例内部；
- 以独立只读文档的形式查看实例内部；
- 跨文档复制粘贴或拖拽元件——跨文档复用电路的唯一路径是"把要复用的东西存成 Project，再当 Subcircuit 引用"。跨文档粘贴不是导航问题而是**跨文档合并**问题：它要求在新文档里重建 Editor ID 映射，同时校验端口位宽、冲突的 Subcircuit 引用路径、以及被复制元件所依赖的一切。更重要的是，Phase 5.5 之后这个平台已经有了一条正确的复用路径，跨文档粘贴会让"引用"和"拷贝"两种复用方式同时存在——而 ADR 0014 选择引用而非拷贝，正是为了避免这种分裂；
- 多窗口；
- 被引用子 Project 的自动重载（见 ADR 0018）。
